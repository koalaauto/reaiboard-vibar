# Architecture

Vibar is one Rust binary. This page is the map: what each file owns, which thread runs what, and how data moves. Read it before changing code.

## Repository layout

```
Cargo.toml            crate "vibar"; repository URL is declared here and nowhere else
default-config.toml   shipped default key layout, embedded into the binary
src/
  main.rs             argument parsing, single-instance lock, wiring of threads and channels
  daemon.rs           Bluetooth session, event loop, layered key lookup, commands, status reporting
  config.rs           config model (serde), migration of old formats, TOML in and out, input names
  actions.rs          shortcut parsing and key simulation (enigo) on a dedicated thread
  mic.rs              virtual microphone: driver install, state machine, on-demand streaming
  coreaudio.rs        asks CoreAudio whether the virtual mic is being recorded from
  autostart.rs        launch-at-login via a user LaunchAgent
  settings.rs         settings window (wry web view), host <-> page messages, config saving
  ui.rs               menu bar item, icons, main menu, tao event loop
ui/settings.html      the whole settings page: HTML, CSS and JS in one file
assets/               icons, generated by scripts/make-icons.py (committed)
scripts/              bundle.sh, ci.sh, devapp.sh, make-icons.py
docs/                 you are here
```

The vendor SDK (`reai-board-sdk`) is a git dependency pinned by revision in `Cargo.toml`. It owns scanning, connecting, the GATT protocol, reconnection, mSBC decoding and the virtual audio driver sources. Vibar never talks to CoreBluetooth directly.

## Threads

| Thread | Owner | What runs there |
|---|---|---|
| main | `ui.rs` | tao event loop, tray icon, menus, the settings window. AppKit requires this to be the main thread. |
| `daemon` | `daemon.rs` | a tokio runtime running `daemon::run`: the SDK, the select loop, the microphone state machine |
| `actions` | `actions.rs` | owns the `Enigo` instance (it is not `Send`) and turns `Action`s into key events |
| `config-watch` | `main.rs` | polls the config file's modification time once a second and reloads it |

Rule: **never block the main thread**, and never touch menu items or the web view from another thread. Other threads talk to the UI only by sending `UiEvent`s through the event loop proxy.

## Data flow

```
 keyboard ──BLE──> SDK ──BoardEvent──> daemon::run ──Action──> actions thread ──> system key events
                                          │
                                          ├──Status──> UiEvent::Status ──> ui.rs ──> menu, icon, settings window
                                          │
 ui.rs / settings page ──Command──> daemon::run   (sleep time, microphone, release keyboard)
 settings page ──JSON over IPC──> ui.rs ──> settings.rs   (load, save, about, ...)
 config file ──config-watch──> Keymap (Arc<RwLock>) shared with daemon::run
```

Three message types carry everything:

- **`daemon::Status`**: daemon to UI. Facts about the world: searching, connected, battery, mode, microphone state, an input was pressed. Add a variant when the UI needs to know something new.
- **`daemon::Command`**: UI to daemon. Requests: set the sleep time, enable the microphone, release the keyboard.
- **`settings` messages**: JSON objects `{ "t": "<type>", ... }` between the page and the host. The page sends `load`, `save`, `sleep`, `release`, `mic`, `mic_remove`, `autostart`, `open_config`, `about`, `open_repo`. The host sends `config`, `state`, `mode`, `input`, `saved`, `notice`.

## Key handling

1. The SDK emits `BoardEvent::KeyPress { key_index, pressed }`. Each physical press is a pair: pressed, then released.
2. `config::key_name(index, knob_swap)` turns the index into an input name such as `knob_cw` or `tab`. The lever (indexes 9 and 10) is handled through `ModeChange` events, never through key presses.
3. `Keymap::lookup(mode, name)` checks the current lever position's layer first, then the default layer.
4. On press the resolved binding is stored in `held`. On release **the same stored binding** is used, so moving the lever while holding a key cannot leave a key stuck down.
5. Actions go to the `actions` thread. Without Accessibility permission the thread keeps retrying and reports the state through `UiEvent::Trusted`.

## Microphone

`mic::MicCtl` is a small state machine ticked every 500 ms from `daemon::run`:

- `Off`, `Installing`, `WaitingKeyboard`, `Idle`, `InUse`.
- Each tick asks `coreaudio` whether the virtual device is running somewhere. If a recorder appears and the keyboard is connected, it asks the keyboard for an audio stream (`start_board_audio`, with a heartbeat every 2 s). When recording stops it waits about 1.5 s before stopping the stream.
- The SDK decodes audio and hands PCM to a `PcmSink`. `MeteredSink` forwards it to the driver and counts levels for the log. The sink must be installed **before** `start()`.
- The driver bundle is compiled by the SDK's build script and copied into `Vibar.app/Contents/Resources` by `scripts/bundle.sh`. `ensure_installed` copies it to `/Library/Audio/Plug-Ins/HAL` with an administrator prompt.

## Extending

**Add an action type** (for example "open URL"): add a field to `config::BindingDetail`, an `Action` variant and its execution in `actions.rs`, handle it in `actions::resolve`, add a type button in `ui/settings.html`, add tests next to the code.

**Add a setting that lives in the keyboard**: add a `Command` variant, handle it in `daemon::handle_command`, report the result with a `Status` variant, show it in `settings.rs::Snapshot` and the page. Remember that writes persist on the device, so write only on explicit user action and skip no-op writes.

**Add a page or control to the settings window**: edit `ui/settings.html`. Strings that users read must follow [design-principles.md](design-principles.md); a unit test enforces the punctuation rules.

**Add an input** (if a new keyboard revision has more): extend `config::INPUTS` and `config::key_name`, add it to the board drawing in the page.

## Testing and debugging

- `scripts/ci.sh` runs formatting, clippy, tests and a release build. Unit tests cover shortcut parsing, config migration and round trips, layered lookup, the microphone state machine and the settings page contract.
- Run without a keyboard or without touching your keys: `vibar --headless --dry-run` prints actions instead of pressing keys.
- Flags: `--headless`, `--dry-run`, `--secs N`, `--probe-audio`, `--demo-icons`, `--open-settings`, `--set-sleep-connected <s>`, `--set-sleep-disconnected <s>`.
- Environment variables for the settings window: `VIBAR_PAGE` (`keys`, `board`, `mic`, `general`), `VIBAR_LAYER`, `VIBAR_SEL`, `VIBAR_THEME` (`light` or `dark`). Together with `--open-settings` they let you screenshot any state without clicking.
- Launching through `open` loses stdout. Use `open -n --stdout /tmp/vibar.out --stderr /tmp/vibar.err build/Vibar.app`.
- A bare binary started from a terminal or an IDE is killed by macOS when it touches Bluetooth, because the responsible process lacks the usage description. Always test through the `.app` bundle.
